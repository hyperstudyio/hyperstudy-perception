# `perception --json`

What the annotator app reads when it drives the CLI as a sidecar (`docs/BACKEND_PLAN.md` step 2 in hyperstudy-annotator).
Put `--json` before the command: `perception --json run graph.yaml --input video=clip.mp4`. `plan` and `run` also take
`--place NODE=PLACE` (where a node runs; `plan` lists its options), `--only NODE[,NODE]` (just those nodes and the
nodes they need; a node's optional input, such as gestures' objects, does not make its node needed: it is read when that
node is chosen too, and left out otherwise) and `--set NODE.KEY=VALUE` (a node's setting; `plan` lists the fixed choices). `run` sends nothing off
the machine without `--allow-uploads` (and then only what the graph's `policy.allow_upload` names), as it downloads no
weights without `--allow-downloads`. The consent is kept with the run: `resume` and `rerun` keep to it (they take
`--allow-uploads` to give it), and a node that would upload in a run without it fails before it starts (`policy`).
`--place` and `--set` may name a node `--only` leaves out. On Apple silicon a node that runs on the GPU has no CPU
place (CPU and GPU share memory), so `--place NODE=native:cpu` is refused for it there. A node placed on another machine (`--place NODE=ssh-gpu1:cuda`, a host from `perception hosts add`) sends its inputs there: it is an upload like an API's, offered only when the graph's `policy.allow_upload` names each kind in its inputs (an input whose type could hold anything, `json.v1` or `text.v1`, counts as every kind) and run only with `--allow-uploads`, whatever its inputs hold. Nodes that call an API or need secrets at run time always run on this machine; a node whose only secret is the token its gated weights are downloaded with (`download_secrets`) runs on a host with the user's yes for keys (`hosts keys HOST on`), where only its prepare gets the token, and never on a cloud machine yet. A cloud place costs money: its price counts against `max_cost_usd` like an API's, so a run that places a node there needs a cap that covers it (`--max-cost-usd`). The app runs `graphs/full.yaml` and picks features with `--only`. `remote run HOST GRAPH` takes `run`'s options and coordinates the whole run on a lab server instead, detached, so it goes on with this machine closed (`remote status`, `attach`, `fetch` and `cancel` reach it later; remote_run.py): running there is consent for HOST to hold the video and every kind the steps make, and the keys the steps declare go with it only if the host has the user's yes (`hosts keys HOST on`).

**The protocol.**
- Every line on stdout is one JSON object with `"v"` (the protocol version, now 1) and `"type"`. Nothing else is
  printed there.
- Adding a field is compatible. Changing what a field means, or removing it, bumps `v`.
- The exit code is 0 on success and 1 otherwise. A failure always ends with an object saying why: `error`, a `plan`
  with `ok: false`, or `run.finished` with `status: "failed"`.
- Times are UTC ISO 8601. Money is USD.

| `event` | the same, as they happen (`resume` and `rerun` stream only their own, not the run's history) | `run`, `node` (or null for the run), `kind` (`task.started`, `task.cached`, `task.retry`, `task.succeeded`, `task.failed`, `run.succeeded`, `run.failed`, ...), `message`, `at` |

| `runs` | `status` | `runs` [{`run`, `pipeline`, `status`, `created_at`}], newest first |
| `exported` | `export` | `run`, `path` (the bundle folder) |
| `nodes` | `nodes` | `nodes` [{`ref`, `id`, `version`, `stage`, `part_of` (the id of the node whose feature it is a step of, e.g. `vision.objects` for `vision.objects-names` and `vision.objects-track`; null for a feature of its own), `description`, `inputs` (name → type), `optional_inputs` (the inputs it runs without when the node feeding one is not chosen), `outputs`, `config` (name → JSON Schema), `places` (where it can run here, best first), `why_not`, `cost` (or null), `uploads`, `secrets` (names, at run time), `download_secrets` (names, for its prepare alone), `models` [{`id`, `source`, `size_gb`, `gated`, `licence_mode`}], `gpu`}] |
| `hosts` | `hosts add`, `list`, `check`, `remove`, `clean`, `keys` | `hosts` [{`name`, `dest` (the ssh destination), `user`, `port`, `identity` (overrides of `~/.ssh/config` given to `add` with `--user`, `--port`, `--identity` (a key file on this machine, absolute); null when not given: every command to the host uses them), `root` (its folder on the host), `caps` {`platform`, `cpu_cores`, `memory_gb`, `accelerators`, `vram_gb` (the largest card's), `tools` (uv, ffmpeg, ffprobe → path on the host, or null)}, `gpus` [{`index`, `name`, `memory_gb`}] (every NVIDIA card nodes may be given there: GPU nodes run on them side by side, one `gpu: exclusive` node per card; empty for a host probed before cards were recorded, which counts as one GPU until `hosts check`. Beside `caps`, not in it: an older CLI reading the same store refuses keys in `caps` it does not know), `probed_at`, `keys` (whether runs coordinated there, `remote run`, may hold the keys their steps declare, and a step placed there the token its prepare downloads gated weights with: `hosts keys NAME on\|off`; false until then, and when the host is added anew)}]: what each host had when it was added or last checked. Its places are `ssh-NAME:ACCELERATOR`. A host that cannot be reached, or a bad name, destination or root, is an `error` |
| `host_probe` | `hosts probe DEST [--user U] [--port P] [--identity FILE] [--root DIR]` | `dest`, `root` (where its folder would be), `caps` and `gpus` (as for `hosts`): what the destination has, reached as `hosts add` would. A connection test: nothing is added and nothing is changed on the host. An unreachable destination is an `error` |
| `cloud_check` | `cloud check [aws\|runpod]` | `provider`, `ok`, `detail`: whether `cloud on` would accept the provider now (SkyPilot reaching AWS; RunPod accepting `RUNPOD_API_KEY`), changing nothing. Exit 0 either way |
| `key_check` | `keys check NAME` | `name`, `ok`, `detail`: whether the provider accepts the key, by requests that cost nothing (`ANTHROPIC_API_KEY`: Anthropic's model list; `HF_TOKEN`: your Hugging Face account, then two per gated model; `RUNPOD_API_KEY`: your pods). A key that is not set, refused, or a provider out of reach is `ok: false` (exit 0); a key with no check is an `error`. The key is sent only to its provider. `HF_TOKEN` also has `account` (its name, or null when not accepted) and `models` [{`id`, `repo`, `revision` (the one the node pins), `nodes` (the refs of the nodes that use it), `gating` (`manual`: the owner reviews each request; `auto`: granted on accepting the terms; null when Hugging Face does not say), `access` (`granted`, `not-granted`: asked for and pending, or never asked, which Hugging Face answers alike; `unknown`: not checked, a token not accepted, a fine-grained token without permission to read gated repos, or no answer), `reason` (why it is `unknown`, else null)}]: every gated model the nodes declare, checked at its pinned revision. Only Hugging Face serving the file (or redirecting to it in its own cache, on the same host; not followed) is `granted`; access is per user, never per organisation |
| `cloud` | `cloud on`, `off`, `status` (`aws`, the default, or `runpod`) | `enabled`, `machine` (e.g. `AWS g6.2xlarge, NVIDIA L4`), `region`, `hourly_usd`. While on, a node with a CUDA runner has the place `cloud:cuda`: a machine started for it and deleted after it. Its `cost_usd` (per option too) is the most it can cost, the hourly price for its deadline (20 minutes plus the video's length, at least 30); the run is charged the time the machine existed, which is also in the node's usage (`machine_usd`). `on` fails (`error`) if SkyPilot cannot reach AWS with the user's credentials. `cloud on|off|status runpod` does the same for RunPod, under `runpod`: `enabled`, `machine` (the GPUs it may get), `region`, `hourly_usd` (the dearest of them, which is what is reserved; the pod is charged at its own price). Its place is `runpod:cuda`; `on runpod` fails if there is no `RUNPOD_API_KEY` or RunPod refuses it |
| `keys` | `keys set NAME`, `list`, `remove NAME` | `set`: `name`, `stored` (`keychain`, or the 0600 file it went to where there is no keychain); the value comes from stdin, never the command line. `remove`: `name`, `removed` (where it was). `list`: `keys` (`name`, `source`: `environment`, `keychain` or a file's path; never values) and `problems` (key files refused, as others can read them). Lookup order: the environment, the keychain, `~/.config/hyperstudy/*.env` files only the user can read |
| `setup.step`, then `setup` | `setup [GRAPH] [--only …] [--place …]` | each step as it ends: `node` (a ref, or empty for the machine's tools), `what` (`tools`, `environment`: its uv project synced from its lock, `models`: its `prepare` script run in it, which fetches its weights), `ok`, `seconds`, `message` (what it said last, or the end of what went wrong); then `ok` and every `steps`. With a graph, the nodes it would run here with its settings; without, every node that can run here with its defaults. Nodes on another machine or an API are left out. Exit 1 if any step failed |
| `graph` | `graph validate` | `valid`, `nodes` (ids in run order), `problems` |
| `models` | `models list` | `models` [{`node`, `id`, `source`, `size_gb`, `gated`, `licence_mode`}], and `nodes` [{`node`, `title`, `service` (the hosted API it calls, or null), `part_of` (as in `nodes`: the app lists a feature's steps, their models and keys, as one), `secrets` (key names it needs: at run time and for its downloads), `download_secrets` (those of `secrets` only its prepare is given), `settings` (as in `plan`, at their defaults)}]: every registered node |
| `artifacts` | `artifacts RUN` | `run`, `artifacts` [{`node`, `name`, `type`, `hash`, `path`}] |
| `event` | `logs RUN` | as above, the run's history (`--follow` keeps streaming; the node's own log text is not included) |
| `canceled` | `cancel`; `remote cancel HOST RUN` | `run`. From `remote cancel`, also `host`, `canceled` (false: the run had ended there, and is left as it was) and `status` (the run's there): the run is recorded canceled there and its running steps stopped; its coordinator starts nothing more, and one that is gone is canceled too (a `remote run --run-id` then finds it ended). `remote fetch` imports it, with no bundle |
| `remote_plan` | `remote run HOST GRAPH --dry-run`; `remote run` when it cannot start | `run` (the id it would have), `host`, `ok`, `problems` [strings: why it would not start; nothing is sent then], `nodes` [{`id`, `uses`, `secrets` (the keys it would be given there), `download_secrets` (the keys only its prepare would be given there), `service`, `uploads` (what it sends its API), `place` (the graph's choice there, or null: HOST picks, as `plan` does here)}], `uploads` (every data kind HOST would hold: the inputs' and every kind the steps make; an output type that could hold anything counts as every kind), `upload_to` (`HOST (SSH)`), `keys` (each key that would be sent -> the steps that declare it, at run time or for downloads; only these are sent), `keys_allowed` (the host's `keys` consent), `max_cost_usd`. With HOST `runpod` (a pod made for the run, pod_run.py), also `pod`: {`deadline_s` (how long the pod may exist: setup, the steps by the video's length, and the linger window; in whole 5 minutes, at least an hour), `linger_s` (`--linger-min`: how long it waits for a fetch once the run ends), `hourly_usd` (the dearest GPU it may get), `reserved_usd` (that for the whole deadline), `api_usd` (the API steps' estimate), `api_cap_usd` (`max_cost_usd` less the reservation: the coordinator there's cap), `video_s`, `gpus` (those it may get: up to $0.60/h, with at least `vram_gb`), `vram_gb` (the largest `minimum_vram_gb` of the graph's CUDA runners), `disk_gb`}; refused too when RunPod is off here, or when `api_cap_usd` would not cover `api_usd`. Event times are the host's. `remote attach` ends with an `error` when the run's coordinator there is gone (the host restarted): `remote run` with its `--run-id` resumes it |
| `pod` | `remote run runpod` | `run`, `pod` (RunPod's id), `name`, `deadline_at` (Unix time: it removes itself then at the latest), `hourly_usd` (what RunPod charges for it), `reserved_usd`. Said once it is made and guard.sh has passed it, before anything is sent to it |

| `remote_started` | `remote run` (a run there ended more than the host's keep days ago, or the oldest while its disk is short, is removed from there at a start or by its sweeper, never within 10 minutes of its end: fetch before then) | `run`, `host`, `started` (false: it was already being coordinated there, or had ended: nothing was started twice), `resumed` (its coordinator there was gone, and was started again), `status` (the run's there). With `--detach`, the last object |
| `plan` | `remote run`, when HOST would not run it | the host's own plan (as above, with HOST's places and cache): a step that cannot run there, weights it lacks without `--allow-downloads` |

| `fetched` | `remote fetch HOST RUN [--output DIR]` | `run`, `host`, `path` (the bundle, exported here from the run just imported, never one the host kept; default `bundles/RUN` in the store, where a later fetch of the run replaces it; a folder holding another run's bundle is refused; null if the run did not succeed), `bundle_problem` (why there is none, or null), `tasks` (task rows imported: each with an attempt number of this store's own, one past its last for that node; unchanged ones are not imported again), `tasks_kept` (tasks this store has run again since the last import, `rerun` here: left as they are, and the run's status and spend with them), `cache_added` (a row for each result whose key this machine computes itself for that step: its node's identity on HOST, config, inputs), `cache_kept` (rows this store already had: never replaced), `cache_refused` (results whose key the host gave is not that one: imported as the run's, never cached), `objects` (brought back, each checked against its hash here). Only a run this machine started there (its record holds the graph and inputs the host's answer is checked against); an answer naming another run, a node not in the graph, an output that is not a store object of its node's type, or a path outside the store's own layouts is refused whole. The run is then one of this store's (`status`, `artifacts`, `export`, `logs`); its tasks' `runner` and `ran_on` say HOST (`ssh-HOST:...`, `coordinator`). A run still going there, or another run of this store's under the same id, is an `error` |
| `error` | any command | `problems` [strings] (an invalid graph, an unknown run, or an unexpected exception) |

A node's `error_code` is one of `transient`, `input`, `schema`, `privacy`, `licence`, `resources` (out of memory: the
message names the setting to lower) and `internal`. Only `transient` is retried. Two more are set by the coordinator:
`budget` (the run's cost cap stopped the node before it started) and `upstream` (canceled because a node it depends on
failed).
